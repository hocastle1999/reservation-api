## 2026-11-08 과거 예약이 쌓이자 방법 A의 처리량이 233건/초에서 14건/초로 떨어짐

**문제**: 부하 측정(`scripts/benchmark_reservations.py --history 20000`)에서 한 자원에 과거 예약 2만 건을 넣고 겹치지 않는 예약 960건을 동시에 보냈다. 방법 A(자원 행 락)의 처리량이 기록이 없을 때 233건/초에서 14건/초로 떨어졌고, p50 응답 시간은 2.3초가 됐다. 방법 B(시간 칸)는 278건/초로 영향이 없었다.

**원인**: 겹침 검사 쿼리의 검색 범위가 아래쪽으로 열려 있었다.

```sql
WHERE resource_id = ? AND start_at < :end AND end_at > :start
```

- 인덱스 `(resource_id, start_at)`로 읽는 범위는 `start_at < :end`뿐이다. 그 자원의 과거 예약이 모두 이 범위에 들어간다. `end_at > :start`는 읽은 다음에 거르는 조건이다.
- `EXPLAIN ANALYZE`로 보니 검사 한 번에 20,000행을 읽고(18.5ms) 0행을 골랐다.
- 방법 A에서는 이 쿼리를 자원 락을 잡은 채로 실행한다. 그래서 18.5ms 동안 그 자원의 다른 요청이 모두 기다린다. 한 줄로 서는 구조라 쿼리가 느려진 만큼 처리량이 그대로 깎였다.
- 단일 요청 테스트로는 데이터가 적어서 전혀 드러나지 않았다.

**해결**: 하한 조건 `start_at > :start - 8시간`을 추가했다(`reservation_service._overlap_conditions`). 예약은 최대 8시간이므로, 겹치는 예약은 반드시 이보다 늦게 시작한다. 결과는 같고 읽는 범위만 줄어든다. 수정 후 같은 조건에서 읽은 행은 0행(0.01ms), 처리량은 219건/초였다.

- 이 최적화는 "8시간을 넘는 예약은 없다"는 전제가 깨지면 겹치는 예약을 놓친다. 그래서 앱 검증만 믿지 않고 DB CHECK 제약 `ck_reservations_duration`도 추가했다.
- 가장 긴(8시간) 예약이 하한 바로 안쪽에 있어도 찾는지 테스트를 추가했다.
- 하루 일정 조회 쿼리도 같은 모양이라 같이 고쳤다.

**배운 점**:

- 겹침(구간) 검사는 B-tree 인덱스로 한쪽 끝만 좁힐 수 있다. 다른 쪽 끝은 도메인 규칙(최대 길이)으로 막아야 한다.
- 락을 잡은 채 실행하는 쿼리는 느려진 만큼 처리량이 직접 깎인다. 락 안의 쿼리는 특히 `EXPLAIN`으로 확인한다.
- 성능 문제는 데이터가 쌓인 상태에서만 보인다. 측정할 때 기록이 많은 상황을 따로 만든다.

## 2026-11-08 부하 측정에서 방법 B(시간 칸)가 데드락(1213)을 냄

**문제**: 32스레드로 같은 자원의 하루 안에서 무작위 예약을 보내는 측정(`random-one-day`)에서 방법 B가 960건 중 3건을 아래 오류로 실패했다. API였다면 500 오류였다. 동시성 테스트(10스레드)를 15번 반복했을 때는 한 번도 나오지 않았다.

```
(1213, 'Deadlock found when trying to get lock; try restarting transaction')
```

**원인 (추정)**: 여러 칸을 INSERT하다 중복 키에 걸린 트랜잭션들이 서로를 기다린 것으로 본다. 데드락의 실제 기록(`SHOW ENGINE INNODB STATUS`)은 PROCESS 권한이 필요해서 앱 계정으로 보지 못했다. 아래는 MySQL 문서에 나온 중복 키 데드락의 동작을 이 상황에 맞춰 본 것이다. root 계정으로 기록을 확인하는 일이 남아 있다.

- InnoDB는 INSERT할 키가 다른 트랜잭션의 아직 커밋되지 않은 행과 겹치면, 그 행에 공유 락(S)을 걸고 기다린다. 앞 트랜잭션이 커밋하면 중복 오류를 받고, 롤백하면 INSERT를 계속한다.
- 예약은 칸을 여러 개 넣는다. 그래서 한 트랜잭션이 "앞 칸은 이미 넣고, 뒤 칸에서 다른 트랜잭션을 기다리는" 상태가 된다. 같은 칸을 여러 트랜잭션이 기다리다 앞 트랜잭션이 롤백되면, 기다리던 쪽들이 모두 공유 락을 가진 채 배타 락(X)으로 올리려 해서 서로를 기다리게 된다.
- 칸을 시간순으로 넣어서 순환 대기를 줄였지만, 이 "롤백 후 동시에 깨어나는" 경우는 순서와 상관없이 생긴다.

**해결**: 예약 생성에서 데드락이 나면 트랜잭션을 처음부터 다시 시도하게 했다(최대 3번, `reservation_service.create_reservation`). 3번 모두 실패하면 503을 돌려준다.

- 데드락은 InnoDB가 한쪽을 통째로 롤백한 것일 뿐, 그 요청이 틀린 것은 아니다. 그래서 409로 거절하지 않고 다시 시도한다. MySQL 문서도 데드락으로 실패한 트랜잭션은 다시 실행하라고 권한다.
- 재시도할 때 경고 로그를 남긴다. 재시도에 성공하면 사용자에게는 안 보이지만, 얼마나 자주 나는지 알아야 하기 때문이다. 측정 스크립트도 이 로그로 데드락 수를 센다. InnoDB 지표(`INNODB_METRICS`)는 PROCESS 권한이 필요해서 앱 계정으로는 읽을 수 없었다.
- 수정 후 같은 측정을 시드 3개로 돌렸다. 데드락은 0~2번 났지만 모두 재시도로 처리되어 오류와 503은 0건이었다.
- 데드락을 흉내 내는 가짜 함수로 "2번 실패 후 성공", "3번 모두 실패하면 503" 테스트를 추가했다.

**배운 점**:

- "락을 직접 잡지 않는 방식"(방법 B)이라고 락이 없는 게 아니다. 중복 키 검사도 락을 쓰고, 여러 행을 다루면 데드락이 날 수 있다.
- 데드락은 완전히 없애기 어렵다. 다시 시도할 수 있게 만들고, 몇 번 나는지 볼 수 있게 하는 것이 현실적인 대응이다.
- 10스레드 테스트에서 안 나온 문제가 32스레드 측정에서 나왔다. 동시성 문제는 동시성 수준을 올려 봐야 보인다.

## 2026-11-08 자원 행을 FOR UPDATE로 잠갔는데도 같은 시간대 예약이 10건 모두 성공

**문제**: 예약 생성은 "자원 행을 `SELECT ... FOR UPDATE`로 잠금 → 겹치는 예약 조회 → 없으면 INSERT" 순서로 만들었다. 같은 시간대 예약 요청 10개를 스레드로 동시에 보내는 테스트(`tests/test_reservation_concurrency.py`)를 돌리자, 1건만 성공해야 하는데 10건이 모두 성공했다.

```
AssertionError: assert Counter({'created': 10}) == Counter({'created': 1, 'conflict': 9})
```

**원인**: MySQL 기본 격리 수준인 REPEATABLE READ의 스냅샷 시점 때문이었다.

- REPEATABLE READ에서 일반 SELECT(잠금 없는 읽기)는 트랜잭션의 **첫 일반 SELECT 시점**에 만든 스냅샷을 계속 본다.
- 실제 요청에서는 예약 전에 인증 의존성(`get_current_user`)이 같은 세션으로 사용자를 먼저 조회한다. 이때 스냅샷이 고정된다.
- 락은 제대로 동작해서 요청들이 한 줄로 섰다. 그런데 뒤 요청이 락을 받은 뒤 겹침 검사를 해도, 락을 기다리기 **전에** 만든 스냅샷을 보기 때문에 앞 요청이 커밋한 예약이 보이지 않았다.
- 가설을 확인하려고 "락 전에 사용자 조회를 하는 경우"와 "안 하는 경우"를 같은 조건으로 돌렸다. 조회를 하면 10건 성공, 안 하면 1건 성공 9건 거절이었다.

**해결**: 앱 엔진의 격리 수준을 READ COMMITTED로 바꿨다(`app/db/session.py`). READ COMMITTED는 문장마다 그 시점의 최신 커밋을 읽는다. 그래서 락을 받은 뒤의 겹침 검사가 앞 요청의 예약을 본다. 수정 후 같은 테스트가 1건 성공, 9건 거절로 통과했고, 5번 반복해도 같았다.

검토했지만 쓰지 않은 방법:

- 겹침 검사도 `FOR UPDATE`/`FOR SHARE`로 읽기: 잠금 읽기는 최신 커밋을 읽어서 결과는 맞다. 하지만 `reservations`의 범위에 갭 락이 걸린다. 자원별 인덱스 범위의 경계에 있는 갭은 옆 자원과 공유되므로, 서로 다른 자원을 예약하는 두 트랜잭션이 데드락에 빠질 수 있다. 자원 행을 잠그는 방식을 고른 이유(docs/erd.md)가 바로 이 갭 락을 피하는 것이었다.
- 예약 직전에 `commit()`으로 트랜잭션을 끊기: 서비스 코드가 "앞에서 무엇을 읽었는지"에 따라 맞고 틀리게 된다. 실수하기 쉽다.

**배운 점**:

- 락을 잡았다고 "최신 데이터를 본다"는 보장은 없다. 락(누가 먼저 하는가)과 스냅샷(무엇을 보는가)은 따로 생각해야 한다.
- 동시성 코드는 단일 요청 테스트로는 절대 검증되지 않는다. 실제로 여러 연결을 동시에 돌리는 테스트를 만들고, 수정 전에 실패하는 것부터 확인한다.
- 테스트도 실제 요청과 같은 순서로 DB를 읽어야 한다. 테스트에서 사용자 조회를 빼면 버그가 숨는다.

## 2026-11-07 Alembic 되돌리기(downgrade)가 MySQL 오류 1553으로 실패

**문제**: 첫 마이그레이션을 `alembic downgrade base`로 되돌리자 아래 오류가 났다.

```
pymysql.err.OperationalError: (1553, "Cannot drop index 'ix_reservations_user_start':
needed in a foreign key constraint")
```

**원인**: Alembic이 자동 생성한 `downgrade()`는 "인덱스 삭제 → 테이블 삭제" 순서였다.

- `reservations.user_id`의 외래키는 `(user_id, start_at)` 복합 인덱스를 써서 검사를 한다. InnoDB는 외래키 컬럼에 인덱스가 반드시 있어야 하기 때문이다.
- 외래키를 만들 때 MySQL이 자동으로 만든 인덱스는, 복합 인덱스가 생기면서 지워졌다. 그래서 이 복합 인덱스가 외래키를 받치는 유일한 인덱스가 되었다.
- 외래키가 살아 있는 상태에서 그 인덱스만 지우려고 하니 MySQL이 거부했다.

**해결**: `downgrade()`에서 인덱스 삭제를 빼고 테이블만 지우도록 고쳤다. 테이블을 지우면 인덱스도 함께 사라진다. 그다음 `downgrade base → upgrade head`를 다시 실행해 왕복이 되는 것을 확인했다.

**배운 점**:

- 자동 생성된 마이그레이션은 그대로 믿지 말고 읽어 본 뒤, 올리기와 되돌리기를 둘 다 실제로 실행해 본다.
- 나중에 인덱스를 바꿀 때도 같은 문제가 생긴다. 외래키 컬럼이 앞에 오는 인덱스를 지우려면 새 인덱스를 먼저 만들고 옛 인덱스를 지워야 한다. 아니면 외래키를 잠시 지웠다가 다시 만든다.

## 2026-11-07 DB 기본값 CURRENT_TIMESTAMP가 한국 시간으로 저장될 뻔함

**문제**: 시각은 UTC로 저장하기로 설계했다. 그런데 `created_at`의 기본값인 `CURRENT_TIMESTAMP`는 DB 세션의 시간대를 따른다. 로컬 MySQL의 전역 시간대를 확인해 보니 `SYSTEM`, 즉 PC 시간대(KST)였다.

**원인**: `DATETIME` 컬럼은 시간대 정보 없이 값만 저장한다. 그래서 세션 시간대가 KST이면 KST 시각이 그대로 들어간다. 이렇게 되면 앱이 넣는 `start_at`(UTC)과 DB가 넣는 `created_at`(KST)의 기준이 9시간 어긋난다.

**해결**: 앱과 Alembic의 DB 연결마다 `SET time_zone = '+00:00'`을 실행하도록 했다. PyMySQL의 `init_command` 옵션을 썼다(`app/db/session.py`, `migrations/env.py`). 확인해 보니 세션 시간대는 `+00:00`이었고, 방금 넣은 행의 `created_at`과 UTC 현재 시각의 차이는 0초였다.

**배운 점**: 서버 설정(전역 시간대)에 기대지 않고 연결 단위로 시간대를 고정하면, 로컬과 배포 환경의 DB 설정이 달라도 같은 결과가 나온다.

## 2026-11-07 Windows에서 alembic.ini에 한글 주석을 넣자 UnicodeDecodeError

**문제**: `alembic.ini`에 한글 주석을 추가한 뒤 `alembic revision`을 실행하자 아래 오류가 났다.

```
UnicodeDecodeError: 'cp949' codec can't decode byte 0xec in position 3563
```

**원인**: Alembic은 `alembic.ini`를 OS의 기본 인코딩(`encoding="locale"`)으로 읽는다. 한국어 Windows의 기본 인코딩은 cp949인데, 파일은 UTF-8로 저장되어 있었다. 오류 추적(traceback)의 `read_config_parser` 부분에서 원인을 찾았다.

**해결**: `alembic.ini`의 주석을 영어로 바꿔 ASCII 문자만 남겼다. 파일 안에도 그 이유를 주석으로 적어 두었다.

**배운 점**: Windows에서는 "파일을 어떤 인코딩으로 읽는가"가 도구마다 다르다. 설정 파일은 ASCII로 쓰는 게 가장 안전하다. 파이썬 코드에서 파일을 열 때는 `encoding="utf-8"`을 항상 명시한다.
